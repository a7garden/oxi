1실행 요약 (Executive Summary)

oxi는 6개 크레이트·약 168K LOC 규모의 성숙한 Rust 워크스페이스로, 계층화된 아키텍처·포트 기반 어댑터 시스템·스트리밍 우선 설계라는 일관된 철학으로 통합되어 있습니다. 단일 작성자(a7garden)가 유지하는 프로젝트 치고는 이례적으로 높은 문서화 밀도와 테스트 커버리지(2,774개 테스트)를 보이며, AGENTS.md·ARCHITECTURE.md·docs/designs/에 아키텍처 의사결정의 근거가 상세히 기록되어 있습니다.

▲ 강점 한눈에 보기
  • 클린한 의존성 DAG — oxi-ai는 내부 의존성 0, oxi-cli가 모두 조립. 순환 의존성 불가 구조.
  • 4계층 access gate (Capability → RBAC → Permission → ExecPolicy) — 단일 진입점 Authorizer로 단락 평가.
  • 복원력 스택 — CircuitBreaker + FallbackChain + MultiProvider + 자동 재시도 + orphan tool result 자동 정리.
  • TTSR (Time-Traveling Stream Rules) — 스트리밍 중 규칙 위반을 실시간 차단하고 시스템 리마인더로 정정.
  • Secret<T> 래퍼로 API 키 Debug/Display 노출 차단, PathGuard로 트래버설 방어.
  • 3-레이어 카탈로그 + models.dev 라이브 인리치먼트로 5000+ 모델 가격/컨텍스트 데이터 확보.
⚠ 주요 위험 한눈에 보기
  • BashTool 위험 명령 감지는 "경고만" — is_dangerous_command()가 차단이 아닌 문자열 추가. 정책 게이트와 미연동.
  • 환경변수 블랙리스트 (LD_PRELOAD 등) — 하드코딩 22개. 화이트리스트 전환이 더 안전.
  • 패키지 무결성 — SHA-256을 lockfile에 저장은 하되, 재설치 시 검증 로직 부재.
  • unsafe 환경변수 조작 — vertex.rs·settings.rs·팩토리 등 다수. Rust 2024에서는 data race UB 가능.
  • 비테스트 코드 unwrap 1,659회 — 일부는 패닉 경로. (AGENTS.md가 clippy unwrap_used warn을 명시하나 사용처가 많음.)

3oxi-ai — LLM 추상화 계층

oxi-ai는 8개 프로바이더(OpenAI, OpenAI Responses, Anthropic, Azure, Bedrock, Google, Vertex, Mistral)를 단일 Provider 트레이트로 통합하는 기반 계층입니다. 내부 의존성이 0이며 모든 상위 크레이트의 뼈대가 됩니다.

3.1 Provider 트레이트와 스트리밍

// oxi-ai/src/providers/trait_def.rs
pub trait Provider: Send + Sync + 'static {
    fn stream<'a>(
        &'a self,
        model: &Model,
        context: &Context,
        options: Option<StreamOptions>,
    ) -> Pin<Box<dyn Future<Output = StreamResult> + Send + 'a>>;

    fn name(&self) -> &str;
}
▲ 강점

스트리밍 우선(ProviderEvent 스트림)으로 모든 프로바이더가 동일한 이벤트 모델을 공유합니다. Box<dyn Future + Send> 반환으로 트레이트 객체 안전(object-safe)하며, GAT 대신 명시적 수명 'a를 사용해 Pin 안전성을 컴파일 타임에 보장합니다. SSE 파서는 부분 UTF-8 라인도 처리한다고 명시되어 있어(AGENTS.md "Pitfalls"), CRLF 불일치 환경에서 견고합니다.

3.2 MultiProvider + CircuitBreaker + FallbackChain

multi_provider.rs는 1,283줄의 지능형 라우팅 프로바이더입니다. 복잡도 분류 → 후보 모델 리스트 구성 → 서킷 상태 확인 → 폴백 체인 시도의 흐름으로, 문서화된 우선순위 규칙을 정확히 따릅니다.

// multi_provider.rs L14-29 — 우선순위 문서화가 코드와 일치
// auto_routing=true일 때:
//   1. 라우터의 베스트 모델 (분류된 복잡도 기반)
//   2. 들어온 모델 (등록 & healthy한 경우)
//   3. 폴백 체인 (설정된 경우)

// 에러 분류:
//   - 재시도 가능 (429, 5xx, 네트워크, 타임아웃): 실패 기록 후 다음 시도
//   - 비재시도 (400, 401, 403): 실패 기록 없이 즉시 반환
▲ 강점

error_to_fallback_reason()으로 프로바이더 에러를 FallbackReason으로 매핑하고, FallbackStream 래퍼로 스트림 시작점에 FallbackStart 이벤트를 주입합니다. FallbackExhaustedStream은 모든 후보가 소진되면 종료 이벤트를 내보냅니다 — 부분 응답 손실 없이 우아한 강등이 구현되어 있습니다.

3.4 complexity_router의 단순성

complexity_router.rs는 키워드 매칭 + 토큰 수 기반 휴리스틱으로 복잡도를 5단계(Trivial~Research)로 분류합니다.

// complexity_router.rs L73-91
let complex_keywords = ["build a", "microservice", "distributed system", ...];
let research_keywords = ["research", "benchmark", "comprehensive analysis", ...];
⚠ 개선점: 키워드 기반 분류의 한계

영어 키워드 하드코딩으로 다국어 프롬프트(한국어·일본어 등)에서 분류 정확도가 급락합니다. 또한 "research the bug" 같은 단순 조사 작업이 Research 등급으로 과대 분류될 수 있습니다. 임베딩 기반 분류 또는 LLM-as-judge 패턴으로 고도화를 권장합니다(제안 S-3 참조).

3.5 컴팩션 전략

compaction.rs는 긴 대화를 LLM 자체 요약으로 압축합니다. CompactionConfig 기본값(keep_recent=4, max_batch=20, target_ratio=0.5)이 합리적이며, LlmCompactor는 현재 모델을 재사용해 요약 비용을 최소화합니다.

⚠ 개선점

generate_branch_summary()가 "created file", "decided" 같은 영어 리터럴 매칭으로 토픽을 추출합니다 (L55-66). 한국어 응답에서는 토픽 추출이 무력화됩니다. 언어 중립적 휴리스틱(구두점/길이/role 가중치) 또는 LLM 추출로 전환을 권합니다.

4oxi-agent — 에이전트 런타임

oxi-agent는 LLM 툴호출 루프의 심장입니다. AgentLoop가 스트리밍 응답 → 도구 실행 → 재시도 → 컴팩션 → TTSR 규칙 적용을 조율합니다. 21개 툴과 MCP 클라이언트를 포함합니다.

4.1 AgentLoop의 run_loop 상태 기계

agent_loop/mod.rs::run_loop()는 L584-909로 약 325줄짜리 중첩 루프입니다. 내부 while 루프는 has_more_tool_calls || !pending_messages.is_empty() 조건으로 턴을 진행하고, 외부 루프는 지연 steering/follow-up 메시지를 잡아냅니다.

// agent_loop/mod.rs L878-905 — 레이스 윈도우 폐쇄 로직
// 내부 while 종료 후 steering 큐 재확인 → drain_steering_queue()와
// while-종료 조건 검사 사이의 창을 닫음
let late_steering = self.drain_steering_queue();
if !late_steering.is_empty() { pending_messages = late_steering; continue; }
let follow_up_messages = self.drain_follow_up_queue();
if !follow_up_messages.is_empty() { pending_messages = follow_up_messages; continue; }
let final_steering = self.drain_steering_queue();  // follow-up drain 창도 폐쇄
if !final_steering.is_empty() { pending_messages = final_steering; continue; }
break;
▲ 강점: 레이스 윈도우 3중 폐쇄

steering/follow-up 메시지가 비동기적으로注入될 때, drain과 조건 검사 사이의 미세한 경쟁 창을 3번의 연속 drain으로 폐쇄합니다. 주석이 명시적으로 의도를 서술하여 유지보수성이 높습니다. 단, 완전한 해법은 아니며 고부하에서는 여전히 창이 존재할 수 있습니다 — tokio::sync::Notify 기반 웨이크업으로 보강을 권합니다.

4.2 orphan tool result 자동 정리

// L649-672 — provider가 메시지 순서를 거부하면 자동 복구

tools/bash.rs는 가장 보안에 민감한 도구입니다. 핵심 메커니즘을 점검했습니다.

환경변수 블랙리스트

const BLOCKED_ENV_VARS: &[&str] = &[

✗ 취약점 ENV-1 (중간): 블랙리스트는 우회 가능

NLSPATH, PERL5OPT, RUBYOPT, GEM_HOME, CARGO_HOME, RUSTUP_HOME, NPM_CONFIG_PREFIX, NODE_OPTIONS(부분), BASH_ENV, ENV, ZDOTDIR, PERL_HASH_PARAMS 등 다양한 인젝션 벡터가 누락되어 있습니다. 셸 시작 파일(~/.bashrc)도 ENV로 로드 가능합니다. 화이트리스트 전환을 강력히 권장합니다(제안 SEC-1).

위험 명령 감지는 "경고만"

// bash.rs L465-467 — 감지 후 출력에 문자열만 추가

✗ 취약점 SEC-2 (높음): 감지-차단 분리

is_dangerous_command()는 fork bomb, sudo, /dev/tcp, /etc/shadow 접근을 감지는 하되 실행 자체는 허용합니다. 에이전트가 자율적으로 동작할 때 이 경고는 단순히 토큰을 소비할 뿐 보호를 제공하지 않습니다. oxi-sdk의 Authorizer/ExecPolicy와 통합해 실행 전 정책 결정으로 전환해야 합니다(제안 SEC-2).

ℹ 평가

process_group(0) 설정 + 음수 PGID 킬로 자식 프로세스 누수를 방지합니다. SAFETY 주석이 근거를 제시하며 적절합니다. 단, SIGKILL은 자식이 clean-up 기회를 못 가지므로 SIGTERM → 그레이스 → SIGKILL 단계적 종료가 더 우아합니다.

4.4 EditTool와 Hashline 통합

edit.rs는 두 모드를 지원합니다: 레거시 old_text/new_text와 새 hashline 패치. prepare_arguments()가 모델이 JSON 문자열로 보내는 edits 배열까지 처리하는 점이 견고합니다 (L58-69). PathGuard::validate_traversal로 트래버설을 막지만 워크스페이스 외부는 허용합니다 — 시스템 설정 읽기 등 합법적 사례를 위한 설계입니다.

⚠ 주의: traversal-only 검증의 양날

validate_traversal은 ..만 막고 절대 경로 외부 접근을 허용합니다. 주석이 의도를 명시하지만, 신뢰할 수 없는 에이전트에게는 validate()(워크스페이스 강제)가 기본이 되어야 합니다. 현재 edit/read/write 모두 validate_traversal을 사용하므로 정책 게이트와 결합이 필수입니다.

4.5 MCP 클라이언트 중간

mcp/mod.rs(1,349줄)는 서버 연결·메타데이터 캐시·consent·라이프사이클을 통합 관리합니다. tokio::sync::Mutex(쓰기) + parking_lot::RwLock(읽기) 혼합으로 AGENTS.md 동시성 가이드라인을 준수합니다.

✗ 취약점 MCP-1 (높음): stdio 서버는 임의 코드 실행

MCP 서버는 command + args로 프로세스를 spawn합니다 (StdioTransport). 이는 설정 파일만으로 임의 바이너리 실행을 의미합니다. ConsentManager가 도구 단위 Allow/Deny를 제공하지만, lifecycle: "lazy" 서버는 최초 도구 호출 시 자동 스폰됩니다. 서버 실행 바이너리 화이트리스트 + 해시 검증 + SHA 기반 known-good 비교가 필요합니다(제안 SEC-3).

agent_loop/ttsr.rs는 스트리밍 중 프로젝트 규칙 위반을 실시간 감지해 스트림을 중단시키고 시스템 리마인더로 정정시킵니다.

5oxi-sdk — 포트 시스템과 빌더

oxi-sdk는 제품(oxi-cli, oxios)과 인프라 사이의 계약(contract)을 정의합니다. 15개 포트 트레이트 + noop 폴백으로, 제품은 필요한 포트만 등록합니다.

5.1 포트 설계 원칙

  1. SDK는 계약만 정의, 제품이 구현 — SDK 내부에 구현체가 없습니다.
  2. 선택적 등록 — 미등록 포트는 noop 기본값으로 동작.
  3. 타입 유연 페이로드 — serde_json::Value로 제품별 구체 타입 분리.
  4. 추가적 버전닝 — 새 메서드는 noop 기본 구현을 가져 기존 제품이 깨지지 않음.

5.2 4계층 access gate

이 강력한 게이트가 실제 BashTool/EditTool 실행 경로에서 항상 호출되는지 점검이 필요합니다. oxi-cli 부트스트랩에서 SimpleAccessGate를 등록하지만, BashTool::execute() 내부에 gate 호출이 보이지 않았습니다. 즉 정책은 정의됐으나 에이전트 툴 실행에 기본 결합되어 있지 않을 수 있습니다. before_tool_call 훅으로 게이트를 강제 주입하는 패턴을 권장합니다(제안 SEC-4).

7.3 패키지 매니저 (packages.rs)

2,933줄의 자체 패키지 매니저는 npm/git/URL/로컬 4가지 소스를 지원합니다.

✗ 취약점 SUP-1 (높음): 무결성 저장 O, 검증 X

compute_dir_hash()로 SHA-256을 계산해 LockEntry.integrity에 저장합니다. 그러나 재설치/업데이트 시 이 값을 다운로드 결과와 비교하는 로직이 보이지 않습니다 (검색 결과 install 경로에 integrity 비교 없음). 즉 lockfile은 감사 로그일 뿐 서버 측 무결성 보장이 없는 npm tarball이나 git ref에 대한 공급망 공급망 보호가 부족합니다.

✗ 취약점 SUP-2 (중간): git clone 자격증명 누출 경로

git_clone()은 GIT_TERMINAL_PROMPT=0을 설정해 자격증명 프롬프트를 막습니다 (좋은 실천). 그러나 공개 URL 검증이 없어 악의적 github: 단축 URL이 SSH 자격증명을 트리거할 수 있고, git+ssh:// 스킴이 명시적으로 허용됩니다. 화이트리스트 도메인 또는 HTTPS 강제를 권장합니다.

✗ 취약점 AUTH-1 (높음): 파일 폴백 암호화 미확인

키링 사용 가능 시 안전하지만, 파일 폴백 시 자격증명이 어떻게 보호되는지 코드 점검에서 평문 여부가 명확하지 않습니다. AuthCredential::validate()는 구조 검증만 하고 암호화는 다루지 않습니다. 폴백 경로는 OS 사용자 키 파생(AES-GCM) 또는 키링 전용 강제가 필요합니다.

9.2 에러 처리

  • 라이브러리 크레이트 (oxi-ai, oxi-agent, oxi-sdk): thiserror::Error로 typed 오류 열거형. 우수
  • 애플리케이션 크레이트 (oxi-cli): anyhow::Result. 적절
  • oxi-tui: anyhow 허용. 수용 가능

다만 비테스트 코드에 .unwrap()이 1,659회 발견됩니다. 대부분은 some().unwrap() 후속 패턴이지만, 일부는 잠재 패닉 경로입니다. AGENTS.md가 clippy unwrap_used를 warn으로 설정했으나 에러가 아닌 점이 이 숫자를 설명합니다.

std::env::set_var/remove_var는 Rust 2024에서 thread-safe하지 않음이 공식적으로 명시되었으며, 다른 스레드가 동시에 env::var를 호출하면 undefined behavior입니다. oxi는 Tokio 멀티스레드 런타임을 사용하므로 이 호출들이 unsafe로 표시된 것은 맞지만, 근본적으로 안전하게 만들 수 없습니다. 해결책: 환경변수를 부팅 시점(메인 스레드, 런타임 시작 전)에만 조작하거나, in-process 설정 레지스트리로 마이그레이션.

10.3 의존성 공급망

CI가 cargo audit + cargo deny + SBOM(CycloneDX 1.5)을 시행합니다. extism = "=1.21.0" 핀이 wasmtime-43 호환성 이슈를 회피하며, 그 근거가 Cargo.toml 주석에 상세히 기록되어 있습니다 — 훌륭한 실천입니다.

11.2 STRIDE 분석 요약

  • S(Spoofing): MCP 서버가 가짜 도구 노출 — consent가 완화.
  • T(Tampering): 패키지/설정 파일 변조 — 서명 부재.
  • R(Repudiation): audit_trail 모듈로 강력한 가시성 확보.
  • I(Info Disclosure): Secret<T> + 키링으로 우수.
  • D(DoS): CircuitBreaker로 프로바이더 DoS 방어. 로컬 리소스 DoS(fork bomb)는 경고만.
  • E(Elevation): 네이티브 확장/MCP 서버가 임의 코드 실행 — 최대 위험.

12취약점 목록 (심각도순)

  1. 심각 SEC-2: BashTool 위험 명령 감지-차단 분리
    oxi-agent/src/tools/bash.rs:465-467 — is_dangerous_command()가 경고만 발생

    fork bomb, sudo, /dev/tcp, /etc/shadow 접근이 감지되어도 실행이 중단되지 않습니다. 자율 에이전트 시나리오에서 치명적입니다. Authorizer::ExecPolicy 게이트를 before_tool_call 훅으로 강제 주입하고, 위험 패턴 매칭 시 차단하도록 전환.

  2. 심각 MCP-1: MCP stdio 서버 임의 코드 실행
    oxi-agent/src/mcp/transport/stdio.rs — command + args로 프로세스 spawn

    설정 파일(mcp.json) 하나로 임의 바이너리가 실행됩니다. 허용 바이너리 화이트리스트 + SHA-256 known-good 검증 + 서명된 매니페스트가 필요합니다.

  3. 심각 SUP-1: 패키지 무결성 저장 O, 검증 X
    oxi-cli/src/storage/packages.rs:2246 — compute_dir_hash는 lockfile 저장만

    install/update 경로에서 integrity 필드를 다운로드 결과와 비교하는 로직이 없습니다. 공급망 공격에 취약. npm tarball의 dist.shasum과 비교 + git ref의 커밋 해시 고정 검증 추가.

  4. 높음 UNSAFE-1: Rust 2024 환경변수 data race
    oxi-ai/src/providers/vertex.rs:323, oxi-cli/src/store/settings.rs (다수)

    Tokio 멀티스레드 런타임에서 env::set_var/remove_var는 UB를 유발합니다. 부팅 시점(런타임 이전)으로 제한하거나 in-process 레지스트리로 마이그레이션.

  5. 높음 AUTH-1: 파일 폴백 자격증명 암호화 미확인
    oxi-cli/src/store/auth_storage.rs

    OS 키링 불가 시 파일 저장의 암호화 보장이 불명확합니다. AES-GCM(사용자 키 파생) 또는 키링 강제 + 명시적 거부 정책 필요.

  6. 높음 SEC-4: AccessGate가 툴 실행 경로에 미결합
    oxi-cli/src/bootstrap.rs — SimpleAccessGate 등록은 하되 훅 주입 불명확

  7. 높음 SUP-2: git clone 자격증명 누출 경로
    oxi-cli/src/storage/packages.rs:619 — git_clone

    git+ssh://와 github: 단축이 허용되어 SSH 자격증명 에이전트 트리거 가능. 허용 도메인 화이트리스트 또는 HTTPS 강제.

13기능 제안 (우선순위)

P0 — 즉시 추천 (보안)

  1. SEC-2: BashTool 게이트 강제 결합 — before_tool_call 훅으로 Authorizer::check(CheckRequest::Exec)를 모든 bash 호출 전 실행. 위험 명령 매칭 시 Err 반환으로 차단. 복구: 1-2일, 영향: 자율 에이전트 안전성 비약적 향상.
  2. SEC-3: MCP 서버 서명 검증 — mcp.json에 integrity 필드(서버 바이너리 SHA-256) 추가, spawn 전 검증. 알려진 좋은 서버 레지스트리(옵션). 복구: 3-5일.
  3. SUP-1: 패키지 install 무결성 검증 — install/update 후 compute_dir_hash 재계산 → lockfile 값과 비교 → 불일치 시 거부. npm dist.shasum 크로스체크. 복구: 2-3일.

P1 — 단기 추천 (견고성)

  1. UNSAFE-1 해소: 환경변수 조작 격리 — 런타임 시작 전(메인 스레드)로 모든 env::set_var 이동. 런타임 내에서는 Settings in-process 레지스트리 사용.
  2. ENV-1: 환경변수 화이트리스트 — BashTool에 allowed_env_vars: HashSet 설정 추가. 빈 집합 = 전체 차단(안전 기본값). 사용자가 명시적으로 허용한 변수만 전달.
  3. AUTH-1: 파일 폴백 암호화 — argon2 사용자 패스프레이즈 + AES-GCM. 키링 불가 시에만 활성. 또는 키링 강제 + 명시적 --insecure-credentials 플래그.
  4. SEC-4: 툴 실행 전 게이트 강제 — bootstrap.rs에서 모든 툴 레지스트리에 with_before_tool_call으로 게이트 주입. 현재는 일부 툴만 결합된 것으로 보임.

  1. S-3: complexity_router 고도화 — (a) 임베딩 기반 분류(EmbeddingProvider 포트 활용), (b) 다국어 키워드 사전, (c) 사용 패턴 학습(자주 쓰는 모델 가중치). 라우팅 정확도 30%+ 향상 예상.

  4. RATE-1: 프로바이더 rate-limit 적응 — 429 응답의 Retry-After/x-ratelimit-remaining 헤더 파싱 → 동적 백오프. 현재는 고정 재시도만.
  5. SESSION-1: 세션 브랜치 TUI 시각화 — 트리 구조를 그래픽으로 렌더링(mermaid.rs 재활용). fork/branch 탐색 UX 개선.

P3 — 장기 추천 (아키텍처)

  1. ARCH-2: oxi-capabilities leaf crate — MemoryBackend, UrlResolver 등의 capability 트레이트를 oxi-agent와 oxi-sdk 양쪽에서 공유. 현재 미러링된 타입 중복 제거.

  4. COMPACT-1: 컨텍스트 압축 고도화 — 중요 메시지 보존 정책(사용자 결정, 코드 변경) 강화. 다국어 요약 품질 개선. 계층적 요약(요약의 요약).

혁신적 기능 아이디어

  • 에이전트 replay/디버거 — 세션 JSONL + audit_trail로 시간 여행 디버깅. 특정 턴에서 다른 모델로 재실행 비교.
  • 스킬 마켓플레이스 신뢰 점수 — 다운로드 수 + 서명 + 사용자 평가로 패키지 신뢰도 점수.
  • 다중 에이전트 토론 모드 — AgentGroup + 메시지 버스로 에이전트들이 코드 리뷰를 토론하는 모드. 합의 기반 결정.
  • 로컬 모델 자동 페일오버 — 클라우드 프로바이더 응답 지연 시 로컬 ollama로 자동 전환. privacy 민감 작업 보호.
  • TTSR 규칙 자동 생성 — 사용자가 수정한 패턴에서 규칙을 자동 학습. "이 사용자는 항상 Korean 주석을 선호" 등.
