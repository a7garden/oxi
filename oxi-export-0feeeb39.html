🔍 결론


이 프로젝트는 무엇인가


pi (Java)를 Rust로 전환한 터미널 AI 코딩 어시스턴트니다. Claude Code, Aider, Cline 같은 제품과 동일 카테고리입니다. 사용자가 터미널에서 LLM과 대화하며 코드를 읽고, 쓰고, 실행하고, 수정하는 것을 하나의 루프로 자동화합니다.


핵심 엔진의 동작 원리


전체 시스템은 하나의 while 루프 요약됩니다:


사용자 입력 → Context 구성 → Provider.stream() → 토큰 스트리밍
    → ToolCall 감지 → Tool 실행 (병렬/순차) → 결과를 Context에 추가 → 반복
    → EndTurn 감지 → 종료

AgentLoop(agent_loop/streaming.rs+ tool_exec.rs가 이 루프의 심장입니다. ProviderEvent스트림을 소비하면서 AgentEvent 변환해 TUI/RPC 계층에 전달합니다. 취소(30초 idle timeout + 500ms 폴링), 회로 차단기, 자동 재시도, 컴팩션이 모두 이 루프 안에 내장되어 있습니다.

개요


oxi TypeScript 프로젝트 pi Rust 포트입니다. 터미널 기반 AI 코딩 어시스턴트로, 6개 워크스페이스 크레이트로 구성된 모듈형 아키텍처를 사용합니다.


oxi-cli (진입점)
  ├── oxi-sdk   (멀티 에이전트 SDK / 빌더 패턴)
  │     └── oxi-agent (에이전트 런타임 / 툴 루프 / MCP)
  │           └── oxi-ai   (통합 LLM API / 10+ 프로바이더)
  ├── oxi-tui   (터미널 UI / Ratatui)
  └── oxi-store (세션 / 설정 / 인증 영속성)

#### 1. oxi-ai— 통합 LLM API (핵심)

| 파일 | 역할 |

|---|---|

| providers/| OpenAI, Anthropic, Google, DeepSeek, Mistral, Groq, Cerebras, xAI, OpenRouter, Azure, MiniMax 등 10+ 프로바이더|

| model_db.rs| 정적 모델 데이터베이스 (비용, 모달리티 정보) |

    🐛 Tool Call 중간에 루프가 끊기는 원인 (버그 분석)


    #### 버그 1: stream_with_retry— 첫 시도에서 non-rate-limit 에러면 즉시 포기


    파일:stream_retry.rs:64-67


    // Non-retryable on the first attempt → bail immediately.
if !is_rate_limit && attempt == 0 {
    return Err(AgentError::Stream(msg));
}

    문제: 첫 시도에서 429 이외의 HTTP 에러 (400, 401, 500 등)가 오면 즉시 에러 반환 그런데 run_loop서 stream_assistant_response Err 반환하면:


    // mod.rs:612-627
let assistant_message = match stream_assistant_response(self, &mut messages, &emit).await {
    Ok(msg) => msg,
    Err(e) => {
        return Ok(self.handle_streaming_error(...).await);
    }
};

    → handle_streaming_error StopReason::Error메시지를 합성하고 루프를 종료다.


    이것이 당신이 보는 문제의 가장 유력한 원인.예를 들어 HTTP 400 ("messages parameter is illegal"이 날아오면:

    1. stream_with_retry 첫 시도에서 에러 → 즉시 Err반환

    2. stream_assistant_response→ Err반환

    3. handle_streaming_error→ 합성 에러 메시지 → return Ok(...)→ 루프 종료

    4. auto-retry 로직조차 도달하지 못함 (auto-retry는 StopReason::Error처리 단계에서 작동)


    > 즉, provider가 tool call 이후에 400 에러를 내면 루프가 완전히 멈춘다.


    #### 버그 2: auto_retry streaming 에러에 도달하지 않음


    auto_retry stream_assistant_response 성공적으로Ok(error_message) 반환했을 때만 작동한다 (mod.rs:631-649). 하지만 stream_with_retry서 발생한 연결 수준 에러는 Err 반환하므로 auto-retry 경로를 우회다.


    두 가지 retry 계층이 있다:

  • Connection-level retry(stream_retry.rs: 429만 재시도, 나머지는 첫 시도에서 포기
  • Message-level retry(retry.rshandle_retryable_error: StopReason::Error메시지에서 regex 매칭으로 재시도

    • 하지만 connection-level에서 non-429 에러가 Err 변환되면 두 계층 모두를 건너뛴다.


    #### 버그 3: Done핸들러의 tool call dedup 로직이 복잡하고 취약


    파일:streaming.rs:286-325


    // Done 핸들러:
let mut preserved_tool_calls: Vec<ContentBlock> = m
    .content.drain(..)
    .filter(|b| matches!(b, ContentBlock::ToolCall(_)))
    .collect();

let mut seen: HashSet<String> = message.content.iter()
    .filter_map(|b| match b { ContentBlock::ToolCall(tc) => Some(tc.id.clone()), _ => None })
    .collect();

preserved_tool_calls.retain(|b| match b {
    ContentBlock::ToolCall(tc) => seen.insert(tc.id.clone()),
    _ => true,
});

*m = message.clone();
m.content.extend(preserved_tool_calls);

    문제:

  • ToolCallEnd이벤트에서 수동으로 누적한 tool call (streaming.rs:247-262)과 Done메시지에 포함된 tool call을 dedup려는 시도
  • 하지만 일부 provider는 Done message.content tool call을 포함하지 않거나, partial누적과 불일치할 수 있음
  • drain(..)로 모든 content를 날려버리고 Donemessage로 교체한 뒤 preserved를 extend하는데, 순서가 뒤바뀜(tool call이 text 뒤에 붙음)
  • Provider마다 streaming 동작이 다른데, 이 로직이 모든 케이스를 커버하지 못할 가능성

    • #### 버그 4: Parallel tool execution에서 cancel 체크 누락


    파일:tool_exec.rs:257-268


    let indexed_results: Vec<(usize, FinalizedToolCall)> = futures::future::join_all(
    pending_futures.into_iter().map(|(i, f)| async move { (i, f.await) }),
).await;

    join_all 모든 future가 완료될 때까지 대기다. Sequential 모드는 각 툴 전에 cancel 체크를 하지만, Parallel 모드에서는 시작 전에만 체크하고, 실행 중에는 취소 불가 긴 툴 실행이 있으면 취소 반응이 느려진다.


    #### 버그 5: has_more_tool_calls로직에서 terminate flag와의 상호작용


    파일:mod.rs:743


    has_more_tool_calls = !executed_batch.terminate;

    그리고 helpers.rs:39-44


    pub fn should_terminate_batch(finalized_calls: &[FinalizedToolCall]) -> bool {
    if finalized_calls.is_empty() { return false; }
    finalized_calls.iter().all(|f| f.result.terminate)
}

    만약 툴 결과의 terminate 어떤 이유로 true 설정되면, tool call이 있어도 루프가 즉시 종료된다.AgentToolResult::success("") 생성하면 terminate기본값이 false야 하지만, after_tool_call hook이 terminate: true 설정하면 조용히 루프가 멈춘다.
